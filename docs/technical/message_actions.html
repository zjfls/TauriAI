🕹️ 消息交互与动作系统

版本: v0.1 | 状态: 草稿 | 更新: 2026-01-08

1. 设计目标

为了支持 Cherry Studio 风格的富交互体验，我们需要建立一套通用的动作 (Action) 协议。这套协议允许后端或前端为任何一条消息动态挂载操作按钮，从而实现：

  • 标准操作：复制、重新生成、语音朗读。
  • 错误恢复：配置模型、重试、查看日志。
  • 特定能力：Claude 的 "Show Thinking"、MCP Tool 的 "Approve/Reject"。

2. 协议定义 (The Protocol)

通用动作结构 (Action Struct)

interface Action {
    id: string;          // 唯一标识 (e.g. "retry_btn")
    label: string;       // 按钮文案 (e.g. "重试")
    icon?: string;       // Lucide图标名 (e.g. "RefreshCw")
    type: ActionType;    // 动作类型
    payload?: string;    // 动作参数
    style?: 'default' | 'danger' | 'primary'; // 视觉样式
}

type ActionType = 
    | 'copy'        // 复制内容 (Payload: 要复制的文本，默认 content)
    | 'retry'       // 重试当前生成
    | 'navigate'    // 内部路由跳转 (Payload: path)
    | 'link'        // 打开外部链接 (Payload: url)
    | 'event';      // 触发自定义事件 (Payload: event name)

4. 场景示例

场景 A: 正常的 AI 回复

后端可以直接注入，或者前端组件默认追加。

{
  "role": "assistant",
  "content": "Rust 是一门系统级编程语言...",
  "actions": [
    { "id": "copy", "type": "copy", "icon": "Copy", "label": "" },
    { "id": "regen", "type": "retry", "icon": "RefreshCw", "label": "" }
  ]
}

场景 B: 错误恢复 (Inline Error Bubble)

这取代了旧的 Error Alert 设计，将错误视为一种特殊的消息。

{
  "role": "error",
  "content": "**配置缺失**\n你没有选择任何模型，无法回答。",
  "actions": [
    { 
      "id": "fix_config", 
      "type": "navigate", 
      "payload": "/settings",
      "label": "去设置",
      "style": "primary"
    }
  ]
}

5. 构建策略与差异化 (Construction & Differentiation)

ActionList 的构建采用 “后端注入 + 前端兜底” 的混合策略。差异化通过以下三个维度的工厂方法实现：

维度 1: 错误类型的差异化 (Backend Error Registry)

由 AppErrorCode 决定。这是强业务相关的。

// src-tauri/src/errors.rs
impl AppErrorCode {
    pub fn get_actions(&self) -> Vec<Action> {
        match self {
            Self::ModelConfigMissing => vec![
                Action::navigate("fix_config", "去设置", "/settings").primary()
            ],
            Self::OllamaServiceDown => vec![
                Action::retry("retry_btn", "重试"),
                Action::link("help_btn", "排查指南", "https://...")
            ],
            // 差异化：网络错误只给重试，配置错误给跳转
            Self::NetworkTimeout => vec![ Action::retry("retry_btn", "重试") ]
        }
    }
}

维度 2: 模型厂商的差异化 (Backend Provider Trait)

由 AiClient Trait 决定。针对特定厂商注入特色功能。

// src-tauri/src/ai_client/traits.rs
pub trait AiClient {
    // 默认无动作，厂商可覆盖
    fn get_provider_actions(&self) -> Vec<Action> { vec![] }
}

// src-tauri/src/ai_client/anthropic.rs
impl AiClient for AnthropicClient {
    fn get_provider_actions(&self) -> Vec<Action> {
        vec![
            // 差异化：只有 Claude 才有 "显示思考" 及其特定 Payload
            Action::event("toggle_thinking", "显示思考过程", "SHOW_THOUGHTS")
        ]
    }
}

维度 3: 最终组装 (Frontend Merger)

前端 MessageAdapter 负责将后端发来的 Actions 与前端通用 Actions 合并。

// src/utils/messageActionBuilder.ts
export function buildMessageActions(msg: Message): Action[] {
    const defaultActions = [
        { type: 'copy', label: '复制' },
        { type: 'regenerate', label: '重试' }
    ];

    // 后端注入的高优先级 Actions (如 Errors, Provider Specifics)
    const backendActions = msg.actions || [];

    // 合并策略：后端 Actions 优先展示
    return [...backendActions, ...defaultActions];
}

5. 扩展性

未来如果要支持新的 Plugin 或 Provider 特性，只需：

  1. 在 Rust 后端 `ActionType` 枚举中添加新类型，或者使用通用的 `event` 类型。
  2. 在前端 `MessageToolbar` 的 Dispatcher 中添加对应的处理逻辑。

# 手写体验优化需求（四）：Android 原生手写层方案

## 1. 背景

Web Canvas 方案可以通过前端优化提升体验，但很难稳定达到系统级便签应用的低延迟手写效果。Android 平台原生输入链路可以直接使用 `MotionEvent`、historical samples、pressure、tilt 等信息，并能更好地控制绘制时机与输入延迟。

本需求旨在为 Android 端引入独立的原生手写层，在不依赖 OPPO 私有 SDK 的前提下，尽可能接近原生书写体验。

## 2. 目标

- 为 Android 平板/手机提供显著优于 Web Canvas 的手写体验。
- 不依赖 OPPO 私有手写笔 SDK。
- 与现有练习系统的数据模型保持可对接。
- 保持桌面端与非 Android 平台继续使用现有 Web 方案。

## 3. 非目标

- 不要求 iOS 同步实现原生手写层。
- 不要求厂商级 palm rejection 效果完全一致。
- 不要求本阶段覆盖所有导出、分享、图片生成场景。

## 4. 范围

### 4.1 包含范围

- Android 原生手写 View / Surface 实现。
- Tauri Android 容器与前端页面的桥接。
- 原生笔迹数据与 Web 数据模型映射。
- 原生层与 Web UI 的显示叠加关系。

### 4.2 不包含范围

- OPPO 专属 SDK 集成。
- iOS 原生手写层。
- 后端批改逻辑重构。

## 5. 需求项

### 5.1 原生手写视图能力

系统应在 Android 端提供原生手写绘制层。

要求：

- 采集 stylus/touch 输入。
- 支持 pressure、tilt、历史采样点（historical samples）等标准 Android 输入能力。
- 支持钢笔、铅笔、橡皮擦等基础工具。

### 5.2 与 Web 页面集成

原生手写层应能与现有练习页面协同工作。

要求：

- 可覆盖在题目页面之上，或嵌入指定作答区域。
- 页面滚动、全屏作答、题目切换需要有明确定义的同步机制。
- 原生层与 Web UI 不得互相遮挡关键操作控件。

### 5.3 数据桥接

原生层采集的笔迹数据应能转换为当前系统可理解的数据结构。

要求：

- 输出至少可映射为 `InkState` / `InkStroke` / `InkPoint`。
- 支持按笔画提交、按批次同步、或退出时同步。
- 同步失败时有回退与错误提示策略。

### 5.4 模式切换

系统应明确定义 Android 平台下何时启用原生手写层。

候选策略：

- 仅练习页启用。
- 仅全屏作答启用。
- 配置项控制启用/禁用。

要求：

- 默认策略明确。
- 异常时可回退到现有 Web 手写实现。

### 5.5 原生性能目标

原生方案应以“明显优于 Web 方案”为目标。

要求：

- 在真机上书写延迟显著下降。
- 连续书写不应出现明显拖影、断线、卡顿。
- 高分辨率设备上仍保持稳定。

### 5.6 错误处理与可观测性

要求：

- 原生层初始化失败时，前端可感知并切回 Web 实现。
- 开发模式下可查看原生输入事件统计、渲染耗时、同步耗时。
- 原生桥接错误需要有明确日志与上下文。

## 6. 验收标准

### 6.1 功能验收

- Android 设备上可使用原生手写层正常书写、清空、撤销。
- 题目切换、全屏切换、页面返回后数据保持一致。
- 批改流程仍能读取手写结果与摘要。

### 6.2 性能验收

- 真机手写体验显著优于现有 Web Canvas 方案。
- 长时间书写下稳定性明显优于 Web 方案。
- 设备兼容性覆盖主流 Android 平板与手机。

## 7. 风险

- 很高风险：需要维护 Android 原生与 Web 双实现。
- 很高风险：跨层数据同步与状态一致性复杂。
- 高风险：Tauri 容器下原生 View 与 WebView 的层级、输入焦点、尺寸同步需要专门处理。
- 中风险：没有厂商私有 SDK，某些高级笔特性可能无法达到系统级体验。

## 8. 建议实施顺序

1. 先做技术预研 PoC。
2. 确定原生 View 叠加方案与桥接协议。
3. 实现最小可用版本（书写 + 清空 + 提交）。
4. 再接撤销、全屏、历史恢复。
5. 最后做回退机制与完整验收。
